## 2026-09-18 — 인프라/설계 방향 검토, 젤리 대비 아키텍처 비교, 창업지원금 리서치

### 배경

토피는 젤리의 설계 패턴을 참고해 시작했지만, 실제 상업 서비스(태국 배우 팬덤 DM 플랫폼,
Bubble 구조 + Weverse 기능 벤치마킹, 전 세계 팬 대상 다국어 지원)를 목표로 하면서
아래 4가지를 점검했다.

### 1. 젤리 대비 아키텍처 비교 — 우선순위 갭 5가지

코드 기준 비교 결과, 백엔드 검증 컨벤션(ID 필드 검증 방식, `ValidationPipe`
`whitelist/forbidNonWhitelisted/transform` 설정, `@Public()` + 글로벌 가드 순서)은
`backend/src/reports/dto/create-report.dto.ts`, `backend/src/app.module.ts`,
`backend/src/main.ts` 등에 코드 레벨로는 이미 계승되어 있다. 반면 아래 5가지는
아직 전혀 갖춰지지 않았고, 상업 운영을 목표로 한다면 우선순위가 높다.

1. **앱 dev/prod 빌드 분리 부재**
   - 젤리는 `app/app.config.ts`가 `APP_VARIANT` 환경변수로 앱 이름/번들ID/scheme/
     GoogleService 파일/네이버·카카오 키를 dev·prod로 분기하고, `app/eas.json`에
     development/preview/production 3개 빌드 프로필이 구성돼 있다.
   - 토피는 `app/app.json`(정적 JSON, `app.config.ts` 아님)만 있고 `eas.json` 자체가
     없다 — 빌드 분리 전략이 전무한 상태. `app/.env.example`도 `EXPO_PUBLIC_API_URL`
     한 줄뿐(소셜로그인/Sentry 등 변수 자체가 아직 없음).
   - `backend/.env.example`의 `ENABLE_DEV_LOGIN` 기본값도 토피는 `"true"`
     (젤리는 `"false"`) — 가드 로직(`NODE_ENV !== production`에서만 동작) 자체는
     안전하지만, 기본값이 실수로 prod에 그대로 나갈 위험을 조금 더 열어둔다.
   - Supabase pooler를 쓸 계획이라면 젤리처럼 `DIRECT_URL`(CLI 마이그레이션 전용
     direct 커넥션)을 분리해둘 필요도 있다 — 토피 `.env.example`엔 아직 없음.

2. **에러 모니터링 전무 (가장 시급)**
   - 젤리는 백엔드(`backend/src/instrument.ts`, `main.ts` 최상단 import)와 앱
     (`app/app.config.ts`의 `@sentry/react-native/expo` 플러그인) 양쪽에 Sentry가
     이미 붙어 있다.
   - 토피는 backend/app 전체에서 Sentry 관련 코드가 0건 — "상업 운영이라 장애
     대응이 체계적이어야 한다"는 목표와 정면으로 배치되는 갭.
   - 추가로 `helmet()`, `trust proxy` 설정도 젤리 `main.ts`엔 있지만 토피엔 빠져 있음.

3. **CI/CD·자동 백업 부재**
   - 젤리는 `.github/workflows/`에 lint/build/typecheck CI, iOS/Android EAS 빌드,
     OTA 업데이트, 매일 DB 덤프 백업(Supabase Storage) 등 5개 워크플로우가 있다.
   - 토피는 `.github` 디렉토리 자체가 없음 — CI, 자동 빌드, 자동 백업 전부 없음.

4. **헬스체크가 단순함**
   - 토피 `backend/src/app.controller.ts`의 `/health`는 `{status:'ok'}`만 반환.
   - 젤리는 `/health`(DB 체크 포함) + `/health/live`(프로세스 응답 여부만 확인하는
     liveness, orchestrator용)로 분리돼 있어 더 정교하다.

5. **문서화·다국어 콘텐츠 확장 미비**
   - 토피 루트에 `CLAUDE.md`가 없고, `backend/README.md`/`app/README.md`는 각각
     Nest/Expo 기본 템플릿 그대로라 컨벤션 문서화가 전혀 안 되어 있다.
   - 다국어: `MessageTranslation` 모델(원문 1회 저장 + 언어별 lazy 캐싱 번역 테이블
     패턴)은 이미 잘 설계돼 있으나, `Actor.legalName`/`chatDisplayName` 등 배우
     프로필·시스템 메시지 같은 정적 콘텐츠의 다국어 저장 구조는 아직 없고, 앱
     UI 자체의 i18n 라이브러리(react-i18next 등)도 아직 도입 전.
   - 참고: 개발 로드맵 아티팩트(https://claude.ai/artifact/2SSV2exLhYfW7zx7jsZP5o)의
     "8단계 진행 중" 항목이 바로 이 번역 파이프라인이며, 태국어+영어부터 지원 예정.

### 2. dev/prod DB·앱 분리 관련 결론

- DB는 이미 `DATABASE_URL` 단일 변수 교체 방식으로 dev/prod 분리가 가능한 구조(젤리와
  동일). Supabase pooler를 쓴다면 `DIRECT_URL` 분리를 미리 넣어두는 게 안전.
- 앱은 위 1번 갭대로 `app.config.ts` + `eas.json` 멀티 프로필 체계를 젤리에서
  그대로 가져와 초기에 세팅해두는 게 좋다 — 나중에 붙이면 번들ID/스킴 변경 등
  마이그레이션 비용이 커짐.

### 6. 소속사 관리계정("콘솔") 권한 설계

#### 지금 코드에 실제로 있는 것

- `Role`: `USER`/`AGENCY_STAFF`/`ADMIN`. 소속사라는 조직 단위는 DB에 없고,
  `User ↔ Actor` 다대다 관계(`Actor.staff`)로 "이 계정은 이 배우 담당"만 표현.
  서비스 레이어의 `ensureStaffOfActor()`가 매 요청마다 담당 여부를 체크.
- `AGENCY_STAFF`가 할 수 있는 것: 담당 배우 대신 방송 메시지 발송(`{{name}}`
  개인화 포함), 답장 열람, 통계 조회(구독자 수 + 마지막 발송일).
- `AGENCY_STAFF`가 **못** 하는 것: 신고 조회/처리(`ADMIN` 전용), 매출/정산 통계
  (아예 미구현), 배우 프로필(소개/사진) 수정(엔드포인트 없음), 스태프 추가/제거
  (셀프서비스 없음, 지금은 관리자가 수동 연결해야 하는 구조로 보임).
- 화면: `console/index`(담당 배우 목록) → `console/[actorId]`(발송/답장/통계 3탭).
  로그인 후 role만 보고 팬 화면/콘솔 화면을 자동 리다이렉트.
- 웹: `app.json`의 `web.output: static` + `react-native-web`으로 기술적으로는
  이미 웹에서 열림. 다만 데스크톱 전용 레이아웃은 없고 모바일 화면을 그대로 씀.

| 배우 대신 메시지 발송 | `AGENCY_STAFF`가 발송 가능 | **폐지 — 배우 본인만 발송 가능**. 지금 `POST /actors/:id/messages/broadcast`의 `@Roles(AGENCY_STAFF, ADMIN)`을 배우 본인 권한 체크로 교체해야 함(아래 8절 `ensureIsActorSelf` 참고) |
| 답장 열람 | `AGENCY_STAFF` 가능 | 유지(소속사도 계속 열람 가능) — 단 노출되는 "팬 이름"이 실명/식별 가능 정보인지 확인 필요(아래 리스크) |
| 구독자 수/발송 통계 | `AGENCY_STAFF` 가능 | 유지 |
| 매출/정산 통계 | 없음 | 추가 권장 — 정산 비율 협상(로드맵 7단계) 이후 신뢰 확보를 위해 최소 "구독자 수 × 단가" 집계는 필요 |
| 신고 처리 | ADMIN 전용 | 유지(이해상충 방지) |
| 배우 프로필 수정 | 없음 | 이것도 발송 권한과 같은 맥락이면 배우 본인 전용으로 가는 게 일관적 — 다음 세션에서 명시적으로 재확인 필요 |
| 스태프 추가/제거 | 없음 | 파일럿(배우 1명)엔 불필요 |

**결과적으로 소속사(`AGENCY_STAFF`) 콘솔은 "발신자"가 아니라 "열람 전용
매니지먼트 대시보드"로 성격이 바뀐다** — 답장/통계(+ 추후 매출 통계)만 보고,
실제 팬과의 커뮤니케이션(메시지·스토리)은 전부 배우 본인 계정이 담당.

#### 리스크

답장 조회 API가 노출하는 "팬 이름"이 실명·연락처 등 식별 정보라면, 태국 팬
데이터를 제3자(소속사)에게 넘기는 것이라 태국 PDPA(개인정보보호법) 상 별도
동의·마스킹이 필요할 수 있음 — 실제 노출 값이 닉네임인지 실명인지부터 확인 필요.

#### 앱/웹 제공 방식 제안

**소속사 콘솔은 웹을 메인으로, 앱은 옵션으로.** 사무실에서 타이핑·사진 업로드·
통계 확인을 하기엔 모바일 UI가 불편하고, Expo web이 이미 켜져 있어 새 프로젝트
없이 `console/*` 라우트에만 데스크톱용 반응형 레이아웃(사이드바, 넓은 테이블)을
얹으면 됨. 팬용 화면은 반대로 앱이 메인(구독·알림·채팅은 모바일 습관에 맞음).
소속사 전용 앱을 별도로 만드는 건 파일럿 단계에선 과함.

#### 수정 — 소속사 콘솔에도 "모니터링" 목적의 앱 채널 필요 (2026-09-18)

배우 본인이 메시지·스토리를 직접 보내는 구조로 바뀌면서(6절/8절 참고), 소속사는
발송 권한을 잃은 대신 **"배우가 실제로 뭘 보내고 있는지 팬이 보는 화면 그대로
모니터링"**할 수 있어야 한다는 요구가 새로 확인됨 — 콘텐츠 검수/품질 관리 목적.
지금 `GET /actors/:id/messages/replies`는 팬의 답장만 보여주고 배우가 보낸
메시지 본문 자체는 안 보여주므로, 이 요구를 충족 못 함.

**결정**: 웹 메인 방침(위 문단)은 유지하되, 앱에도 **모니터링 알림 채널**을
추가하기로 함 — 새 답장/신고 발생 시 푸시 알림 외에, **배우가 새 메시지·스토리를
보낼 때도 소속사 담당자에게 푸시 알림**을 보내고, 앱에서 그 알림을 눌러 (팬이
보는 것과 동일한 형태로) 배우가 보낸 메시지 내용을 읽기 전용으로 바로 확인할 수
있어야 함. 즉 "소속사 전용 앱을 새로 만드는" 게 아니라, 팬 앱과 같은 코드베이스
안에서 `AGENCY_STAFF` 로그인 시 접근 가능한 **읽기 전용 대화 열람 화면**을
추가하는 형태 — 발송 권한은 없지만 조회 권한은 앱에서도 필요하다는 것.

### 7. 신규 기능 아이디어 — 라이브 방송 + 24시간 소멸 스토리

모두에 이 변경을 반영해서 동기화해둘 필요가 있음(이 md는 토피 저장소 쪽 기록이고,
클로드 아티팩트 두 문서는 사용자가 직접 갖고 있으니 그쪽도 업데이트 권장).

기술적으로 이 둘은 성격이 완전히 다른 작업이라 구분해서 계획해야 함:

- **24시간 소멸 스토리** (난이도 낮음, 기존 구조 확장으로 가능)
  - 지금 `Message` 모델(발신자 구분, 미디어 타입 enum)을 그대로 확장하거나,

    레코드는 조회 API에서 제외하거나 배치로 정리(cron).

    그대로 재사용 가능 — 스토리지 비용이 소멸 후에도 남지 않도록 만료 시 실제
    파일도 삭제하는 정리 잡이 필요.

- **라이브 방송** (난이도 높음, 완전히 새로운 인프라 축) — **보류 결정 (2026-09-18)**
  - 실시간 스트리밍은 지금 스택(NestJS + Postgres + FCM 푸시)에 없는 완전히
    새로운 컴포넌트라 LiveKit/Agora/Mux 같은 서드파티 인프라 연동이 필수인데,
    배우 1명 파일럿 단계에는 과하다고 판단해 **뒤로 미루기로 결정**. 스토리

    분류를 그대로 유지한다(재검토 불필요 — 오히려 이번 결정으로 재확인됨).

### 8. 24시간 소멸 스토리 — 스펙 결정 (2026-09-18)

사용자와 상의해서 아래 4가지를 확정함.

| 결정 항목 | 결정 |
|---|---|
| 업로드 주체 | **배우 본인이 앱에서 직접** (소속사 콘솔이 아님) |
| 노출 시간 | **고정 24시간** (소속사 설정 불가) |
| 조회 확인 | **조회한 팬 목록까지** 배우/소속사 콘솔에서 확인 가능 |
| 공개 범위 | **구독자 전용** (비구독자 미리보기 없음, 메시지와 동일 정책) |

#### 중요한 파급 효과 — "배우 본인 계정" 자체가 새로 필요함

지금 구조엔 **배우가 직접 로그인하는 개념이 없다.** `Role`은 `USER`/
`AGENCY_STAFF`/`ADMIN` 세 가지뿐이고, 배우 대신 행동하는 주체는 항상
`AGENCY_STAFF`(소속사 담당자)다(`ensureStaffOfActor`가 "이 계정이 이 배우의
스태프인가"만 검사). "배우 본인이 직접 스토리를 올린다"를 구현하려면 새 계정
체계가 필요했는데, 이후(6절) 메시지 발송 권한까지 소속사에서 완전히 제거하기로
결정하면서 **아래 1번으로 확정됨** — 이제 메시지·스토리 둘 다 배우 본인 계정이
있어야만 성립하는 구조라, 계정을 공유하는 절충안(2번)은 의미가 없어졌다.

1. **[확정]** `Role.ACTOR`를 새로 추가하고 `Actor`에 `selfUserId`(1:1, 배우 본인
   계정) 필드를 신설. 소속사 스태프 계정(`AGENCY_STAFF`, 열람 전용)과 배우 본인
   계정(`ACTOR`, 메시지·스토리 발신용)을 명확히 분리. 권한 체크는
   `ensureStaffOfActor`와 별개로 `ensureIsActorSelf(userId, actorId)`를 새로
   만들어야 하고, 기존 `POST /actors/:id/messages/broadcast`의
   `@Roles(AGENCY_STAFF, ADMIN)`도 `ensureIsActorSelf` 체크로 교체해야 함.
2. ~~배우 본인도 `AGENCY_STAFF` 계정을 공유해서 로그인~~ — 소속사 발송 권한
   자체가 없어졌으므로 폐기.
3. 배우 전용 앱 화면(카메라 촬영 → 즉시 업로드, 메시지 작성)이 새로 필요 —
   지금 `console/*`의 발송 탭은 소속사용으로 만들어졌던 화면이라 배우 본인용으로
   그대로 못 씀. 팬 앱과도, 소속사 콘솔과도 다른 "배우용 진입점"을 어디에 둘지
   (같은 앱 안의 별도 탭 vs 완전히 분리된 진입) 결정 필요 — 다음 세션 논의 대상.

#### `Story` 데이터 모델 설계안

```
model Story {
  id         String   @id @default(uuid())
  actorId    String
  mediaType  MessageMediaType   // 기존 enum 재사용 (PHOTO/VIDEO/VOICE)
  mediaUrl   String
  createdAt  DateTime @default(now())
  expiresAt  DateTime           // createdAt + 24h, 생성 시 계산해서 저장
  views      StoryView[]
}

model StoryView {
  id        String   @id @default(uuid())
  storyId   String
  fanUserId String
  viewedAt  DateTime @default(now())
  @@unique([storyId, fanUserId])
}
```

- 조회 API(`GET /actors/:id/stories`)는 `expiresAt > now()`인 것만 반환 — 기존
  메시지의 "소급 열람 불가" 필터링 패턴과 동일하게 서비스 레이어에서 처리.
  DB 레코드 자체는 즉시 안 지우고, 별도 cron(예: 매시간)으로 만료된 `Story`와
  연결된 미디어 파일(Supabase Storage 등)을 정리 — 스토리지 비용이 계속 쌓이지
  않게 하기 위함.
- 구독자 전용이므로 조회 API는 메시지 조회와 동일하게 "활성 구독 여부" 체크를
  먼저 거침.
- 조회 목록(`StoryView`)은 배우/소속사 콘솔에서 `GET /actors/:id/stories/:storyId/views`
  같은 엔드포인트로 노출 — `ensureStaffOfActor`(혹은 위 `ensureIsActorSelf`)로
  권한 체크.

## 2026-09-18 (계속) — 문서 구조 정리, 소속사 모니터링, 콘텐츠 모더레이션/회원 관리, 사업 체크리스트

### 문서 구조 정리 + 자동화 정책

`docs/brand/` → `docs/product/brand/`로 이동하고, `docs/product/`(비개발자용 기획 문서)와
`docs/engineering/`(개발자용 기술 문서)를 신설. 이 파일(`deployment-readiness-plan.md`)은
날짜순 세션 로그 역할만 계속하고, "지금 기준 최신 상태"는 새 폴더의 문서로 정리.

사용자가 "작업 마무리될 때마다 자동으로 문서를 만들거나 업데이트해달라"고 요청 —
루트 `CLAUDE.md`를 새로 만들어 이 규칙을 명시함. git에 커밋되는 파일이라 다른
계정/세션에서 이 저장소를 열어도 동일하게 적용됨(세션 로컬 설정에는 넣지 않음).

### 소속사 콘솔에 "모니터링" 채널 필요 (앱 포함)

배우 본인이 메시지·스토리를 직접 보내면서, 소속사는 "배우가 실제로 뭘 보내는지 팬이
보는 화면 그대로" 확인할 수 있어야 한다는 요구가 새로 확인됨(콘텐츠 QC 목적). 결정:
소속사 콘솔은 웹이 메인이라는 방침은 유지하되, 새 메시지/스토리 발송 시 소속사 스태프
에게 푸시 알림을 보내고 앱에서도 읽기 전용으로 열람 가능해야 함. 상세는
`docs/product/feature-decisions.md`, 기술 설계는 `docs/engineering/architecture-notes.md` 참고.

### 콘텐츠 모더레이션 / 회원 관리 — 조사 후 스펙 확정

오전에 조사한 결과(신고 처리 외엔 필터링/회원 제재 기능이 전혀 없음)를 바탕으로 스펙을
정함:

- 팬 답장에 금칙어(욕설/음란한 표현)가 있으면 **전송 자체를 차단**(마스킹 아님).
- 금칙어 목록 언어 범위: 처음엔 태국어+영어만 검토했으나, **한국어를 추가해 한국어·
  태국어·영어 3개 언어**로 최종 결정 — 운영자(대표) 본인이 한국어 목록을 직접 관리하기
  편해야 한다는 이유.
- "블랙리스트 관리"는 금칙어 목록 관리를 의미 (계정 자체를 막는 것과는 별개 개념으로 정리).
- 팬 계정 제재는 **일시정지 + 영구차단** 2단계.

제품 결정은 `docs/product/feature-decisions.md`, 스키마/구현 설계안(`BannedWord` 모델,
`User.status` 등)은 `docs/engineering/architecture-notes.md`에 정리. 아직 코드로
구현하지는 않음 — 다음 세션에 진행 여부 확인 필요.

### 사업 운영 체크리스트 제안

사용자가 "상업화가 처음이라 놓치는 게 있을 것 같다"고 해서, 기능이 아닌 사업 운영
관점에서 중요한 4가지를 제안하고 `docs/product/business-compliance-checklist.md`로
정리:

1. **인앱결제(IAP) 의무** — Apple/Google이 앱 내 디지털 구독 상품에 자사 결제를
   강제하므로, 결제 아키텍처를 지금부터 IAP 전제로 설계해야 함(가장 시급, 나중에
   고치기 제일 비쌈).
2. 이용약관/개인정보처리방침/자동갱신 고지 — 앱스토어 심사 요건이자 다국가 소비자
   보호법 이슈, 변호사 자문 필요(사업 로드맵 7단계 법률 자문 시 같이 처리 권장).
3. 태국 소속사에 대금 지급 시 원천징수/해외송금 신고 — 세무사 자문 필요.
4. 미성년 팬 비중이 높은 팬덤 서비스 특성상 연령/미성년자 결제 정책 필요.

사용자가 4개 항목 전부 필요하다고 확인 — **구현 범위에 포함, 실제 착수는 다음
세션부터**로 결정. `subscriptions.service.ts:20`에 원래부터 "결제는 계약 성사 후
IAP로 붙일 예정"이라는 주석이 있어서 IAP 방향은 기존 계획과도 일치함을 확인.
기술 작업 목록은 `docs/engineering/architecture-notes.md`에 정리.

## 2026-09-18 (계속) — IAP 스캐폴딩, 사업자 형태 논의

### 사업자 형태 (개인사업자 vs 법인, 태국 법인 필요 여부)

IAP 작업 도중 사용자가 "개인 출시 후 나중에 사업자 등록"이라는 예전 조언(예비창업패키지
자격 유지 목적)을 다시 짚어봄 — 두 가지 새 리스크를 발견:

1. **애플 개발자 계정은 Individual→Organization 공식 전환 절차가 없음** — 나중에
   법인으로 바꾸려면 사실상 새 계정을 만들어야 해서(App 이전 기능이 있지만 제약 많음,
   구독 상품 재설정 필요할 수 있음), 개인 계정으로 먼저 앱을 올려두면 나중에 문제가 됨.
   구글 플레이는 계정 이전이 상대적으로 유연해서 이 리스크가 작음.
2. 태국 소속사와 실제 계약(수익 배분 등)까지 갈 때 사업자 등록 없는 개인은 신뢰도/계약
   주체 문제가 생길 수 있음.

→ 예비창업패키지(최대 1억, 사업자 등록 전 신청 조건) 자격 유지보다, **앱스토어 개발자
계정을 만들기 전에 개인사업자를 먼저 등록**하는 쪽이 낫다는 쪽으로 의견 제시함(최종
결정은 아직 안 함 — 초기창업패키지 트랙도 남아있어서 사용자가 판단할 부분). 태국
법인은 초기엔 불필요, 한국 사업자로 해외 계약 형태로 정산하면 됨.

개인사업자 vs 법인사업자 비교, "법인차 저렴하다"는 통념이 최근 세법 강화로 예전만큼
유리하지 않다는 점도 설명함 — 문서화하지 않고 채팅으로만 답변(순수 자문 성격, 결정
사항 아님). 필요하면 나중에 `docs/product/business-compliance-checklist.md`에 추가.

### IAP(인앱결제) 스캐폴딩

- `Subscription`에 IAP 관련 필드 추가, `POST /actors/:id/verify-purchase` 신규
  (기존 샌드박스 `subscribe`는 유지).
- Apple은 `@apple/app-store-server-library`로 StoreKit2 서명 트랜잭션을 로컬 검증
  (레거시 `verifyReceipt` 방식 아님), Google은 Play Developer API를 기존
  `google-auth-library`로 직접 호출.
- 앱엔 처음에 `react-native-iap`를 설치했다가, 이 라이브러리가 **"Expo 프로젝트는
  미지원, `expo-iap` 쓸 것"**이라고 공식 문서에 명시된 걸 뒤늦게 확인하고 되돌림 —
  `expo-iap`로 다시 설치, `usePurchaseSubscription` 훅 작성.
- `backend`/`app` 양쪽 `tsc`/lint/build 통과 확인.

실제 결제 테스트는 앱스토어/플레이스토어에 구독 상품을 등록해야 가능 — 사용자가
스토어 콘솔에서 직접 해야 하는 부분이라 이번 세션에서는 여기까지. 상세 체크리스트는
`docs/engineering/architecture-notes.md`의 IAP 절 참고.

이걸로 대기 목록 7개 중 IAP까지 사실상 마무리(스캐폴딩 기준). 남은 건 약관/개인정보
처리방침 화면, 연령/미성년자 정책 2개.
