# 제품 기능 결정 사항

지금까지 논의를 거쳐 확정된 제품 결정들을 주제별로 정리한다. "왜 이렇게 정했는지"까지
적어서, 나중에 다시 논의할 때 같은 논의를 반복하지 않도록 한다. 기술적인 구현 방법은
[`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md) 참고.

## 메시지·스토리는 배우 본인만 보낸다

처음엔 소속사 담당자가 배우 대신 메시지를 발송하는 구조였지만, **소속사의 발송 권한을
완전히 없애고 배우 본인만 메시지·스토리를 보낼 수 있게** 바꿨다(2026-09-18). 이유:
소속사가 배우 이름으로 대신 말하는 구조를 보수적으로 열어두고 싶지 않다는 판단.

- 대신 소속사는 **"배우가 실제로 뭘 보내고 있는지" 읽기 전용으로 모니터링**할 수 있어야
  한다 — 팬이 보는 화면 그대로, 콘텐츠 품질 관리 목적. 새 메시지/스토리가 나가면 소속사
  담당자에게 알림도 가야 한다.
- 소속사 콘솔은 웹이 메인이지만, 이 모니터링/알림만큼은 앱에서도 볼 수 있어야 한다 —
  담당자가 자리를 비웠을 때도 확인할 수 있어야 하기 때문.

서버 쪽(알림 발송 + 배우가 보낸 내용 조회 API)은 구현 완료(2026-09-18). 소속사
콘솔(앱)의 "발송" 탭도 이제 이 API로 보여주는 읽기 전용 "모니터링" 탭으로
바뀌었다(소속사는 이제 발송 권한이 없으니까). 다만 이건 지금 앱 화면 하나로만
되어 있고, 별도 데스크톱용 웹 화면은 아직 없음(원래 계획한 "웹이 메인" 방침은
그대로 유효, 구현만 아직).

## 1차 점검 후 결정 (2026-09-28)

근거와 배경: [`qa-review-2026-09-28.md`](./qa-review-2026-09-28.md) B절.

- **1차에 넣기로 한 것**: 회원 탈퇴, 가입 시 약관·개인정보 동의(기록), 고객센터(문의하기), 가입 직후 24시간
  닉네임 자유 수정, 팬 답장 횟수 제한(스타 메시지 하나당 3개, 설정값), 스타의 보낸 메시지 삭제, 운영자의 신고된
  스타 메시지 숨기기, 미성년자 기준 국가별 설정(잠정 한국 14세·태국 20세 → 변호사 확정), 통계용 데이터 기록 시작
  (가입 경로·국가·해지 시각 등, 화면은 2차).
- **2차로 미룬 것**: 배우별 알림 끄기, 영구차단 우회 방지(기기·휴대폰 인증), 스타 장기 미발송 정책(소속사 계약부터).
- **해지 방식**: 실제 결제를 붙이면 **해지해도 결제 기간 끝까지 이용**(스토어 표준). 지금 데모는 즉시 종료.
- **다시 구독했을 때 이전 대화**: 버블처럼 **안 보임**. 대신 **반드시 미리 알린다** — 해지 확인창에 "구독이 끝나면
  지금까지의 대화를 볼 수 없고, 다시 구독해도 이전 대화(받은 메시지·보낸 답장)는 다시 볼 수 없어요. 간직하고 싶은
  사진·음성·영상은 미리 저장해 두세요"를 보여주고, 약관 초안 "2. 구독 및 결제"에도 같은 내용을 넣었다. 실제 결제를
  붙이면 해지는 스토어 화면에서 하게 되므로, 스토어로 보내기 **전에** 이 안내를 앱에서 먼저 보여줘야 한다.

## 배우 프로필 — 공식 프로필은 운영자, 채팅방 프로필은 배우 (2026-09-28)

- **공식 사진·공식 이름**(배우 찾기·배우 소개 화면): 운영자가 관리. 바꾸려면 운영자에게 요청.
- **닉네임**: 따로 "대화방 이름"이라는 개념은 없고, **배우가 직접 정한 자기 닉네임이 곧 채팅방에 보이는
  이름**이다. 배우가 스튜디오 "내 프로필"에서 언제든 바꿀 수 있다(팬과 달리 변경 주기 제한 없음). 운영자가
  배우를 등록할 때 첫 닉네임을 넣어 두고, 이후엔 배우가 바꾼다. 소속사는 닉네임을 대신 바꾸지 않는다.
- **대화방 사진**: 배우 본인과 소속사 직원 둘 다 바꿀 수 있다(소속사가 계정 관리를 돕는 경우가 많아서).
- **인증 배지(✓)는 넣지 않는다** — 토피엔 운영자가 직접 등록한 스타만 있어서 모든 스타가 이미 공식이다.
  배지는 누구나 계정을 만들 수 있는 서비스에서 가짜 계정과 구분하려고 쓰는 것.

## 배우·소속사 직원 계정은 어떻게 만드나 (2026-09-28)

- 스타와 소속사 직원도 팬과 똑같이 **앱에서 소셜 로그인으로 가입**한 뒤, 운영자가 "회원 관리"에서 역할을
  "배우" 또는 "소속사 직원"으로 바꿔 준다. 별도 가입 화면이나 초대 링크는 1차에 만들지 않음.
- 배우 계정은 "배우 관리"에서 해당 배우에 **본인 계정으로 연결**해야 메시지를 보낼 수 있다. 소속사 직원은
  회원 관리에서 소속사를 지정하면 그 소속사 배우 전원을 모니터링한다.
- **구독 중인 팬 계정은 배우·직원으로 바꿀 수 없다**(구독 해지 후 변경) — 돈을 낸 팬 계정에 관리 권한이
  섞이지 않게 하기 위함. 운영자 계정은 앱에서 만들 수 없고 개발자가 직접 만든다(권한 탈취 방지).
- 배우 사진은 공식 사진(배우 찾기·소개)과 대화방 사진(채팅방) 두 가지 — 위 "배우 프로필" 참고.
- 구독료는 운영자가 배우별로 입력하지만, **실제 결제 금액은 앱스토어·구글플레이에 등록한 상품 가격**이
  기준이다 — 가격을 바꿀 땐 스토어 상품 가격도 같이 바꿔야 한다(화면에도 안내 문구 있음).

## 인용 답장 — 구현 완료 (2026-09-28)

- 스타는 "팬 답장 모아보기"에서 팬 메시지를 골라 **답장하기** → 보내는 메시지 위에 카톡처럼 인용 부분(닉네임 +
  내용 앞부분)이 붙는다. 이 답장은 **모든 구독자에게** 보인다(2026-09-28 확정대로). 보내기 전 입력창 위에
  "모든 구독자에게 보이고, 팬은 닉네임으로 표시돼요" 안내가 뜬다.
- 같은 배우 채널의 **팬 메시지만** 인용할 수 있다.
- 인용된 팬이 정지·차단되거나 그 메시지가 신고로 처리되면, 이미 보낸 인용 답장에서도 인용 부분이
  **"가려진 메시지"**로 바뀐다(스타의 답장 내용 자체는 그대로).
- 팬끼리 서로의 답장은 여전히 안 보인다 — 스타가 인용한 것만 공개된다.
- 2차 후보: 내 메시지가 인용되면 그 팬에게 따로 알림.

## 닉네임 (2026-09-28 구현, 세부 규칙은 잠정)

- 팬은 가입 마지막 단계에서 닉네임을 정한다. 앱 전체에 하나(배우별로 따로 아님).
- **다른 사람과 같아도 된다**(버블 방식) — 대신 헷갈리지 않게, 스타·소속사·운영자 화면에서는 닉네임 옆에
  짧은 구분 태그(예: `#A1B2`)가 붙는다. 팬들끼리는 태그가 안 보인다.
- **막는 것**: "공식·운영자·관리자·토피" 같은 공식처럼 보이는 단어, 배우 이름과 똑같은 닉네임, 금칙어,
  눈에 안 보이는 특수문자(다른 사람 닉네임 흉내 방지). 최대 20자.
- **바꾸기**: 마이페이지에서 7일에 한 번(처음 정할 때는 제한 없음) — 스타가 인용한 직후 바꿔서 숨는 걸
  막는 정도.
- 쓰이는 곳: 배우 메시지의 이름 자리(`{{name}}`), 알림, 스타·소속사가 보는 팬 답장 목록. 소셜 로그인에서
  받은 이름(실명일 수 있음)은 이제 이런 화면에 나오지 않는다.
- 태그 표시, 7일, 금지 단어 목록은 잠정 — `STATUS.md` "출시 전 확정할 정책".

## 관리 화면은 웹과 앱 둘 다 (2026-09-28 확정)

소속사와 운영자 **모두 PC 웹 화면이 필요**하다(사용자 결정) — 정산처럼 PC에서 넓게 확인해야
하는 일이 있어서. 앱은 소속사의 모니터링·알림, 운영자의 급한 처리용으로 계속 쓴다.

- 토피는 앱과 웹이 **같은 코드**라서 지금 화면도 이미 브라우저에서 열린다. "웹을 만든다"는 건
  새로 개발하는 게 아니라 **PC 화면에 맞게 넓게 배치하는 작업**.
- 시기: 1차에서는 지금 화면을 웹·앱에서 그대로 쓰고, PC용 배치는 **2차에 정산 기능과 함께**. → 2026-09-29 정산과 함께 만듦(아래 "정산" 절).

**소속사 웹/앱 역할 나누기 (2026-09-28 확정)** — "앱은 가볍게, 웹은 전부":

| | 앱 | 웹 |
|---|---|---|
| 목적 | 이동 중 빠른 확인·대응 | 책상에서 자세히 확인·관리 |
| 모니터링(배우가 보낸 메시지) | ✅ 핵심 | ✅ |
| 팬 답장·신고·차단 | ✅ 핵심(알림 받고 바로 처리) | ✅ |
| 통계 | 요약(구독자 수 등) | 기간별 상세·그래프 |
| 정산 내역·매출 | ❌ | ✅ 웹 전용 |
| 이적·계약 기록 | ❌ | ✅ 웹 전용 |

- 웹에서 모니터링을 빼지 않는 이유: 사무실 PC로 일하는 직원이 폰을 꺼내지 않아도 되게. 같은 코드라 비용도 거의 없음.
- 정산은 표가 크고 민감한 정보라 웹 전용 — 폰 화면 노출도 줄어듦.
- 1차 범위는 그대로(지금 콘솔 = 앱 기준 기능). 웹 전용 기능은 2차 정산과 함께 만든다.

**운영자도 같은 원칙, 앱은 하나로 (2026-09-28 확정)** — 소속사·운영자 전용 앱을 따로 만들지 않고, 같은 앱에서
로그인한 역할에 따라 화면이 달라진다(버블처럼 소속사별 앱, 위버스처럼 입점센터 앱을 따로 두지 않음 — 개발 인력
대비 유지 부담이 커서).

| | 앱 | 웹 |
|---|---|---|
| 소속사 | 모니터링, 팬 답장·신고·차단, 요약 통계 | 전부 + 정산·상세 통계·이적 기록 |
| 운영자 | 신고 처리, 회원 정지·차단, 요약 총계(오늘 가입자·구독자·대기 신고 수 등) | 전부 + 배우·소속사 등록, 통계 대시보드(그래프), 정산 |

- 신고 처리를 앱에 두는 이유: 문제 메시지는 빨리 가려야 해서 PC 앞에 없어도 알림 받고 처리할 수 있게.
- 앱에서 빼는 것: 정산처럼 크고 민감한 표, 배우 등록처럼 입력이 많은 관리 작업(웹에서).
- 필요해지면(예: 소속사가 자기 이름의 앱을 원함) 같은 코드로 빌드만 하나 더 만들 수 있다.

## 음성 메시지 — 카톡처럼 (2026-09-28)

스타가 보낸 음성은 **음파 모양 막대 + ▶ 재생 버튼 + 길이**로 보인다. 재생하면 들은 만큼 막대가
진해지고 남은 시간이 줄어든다. 다른 음성을 누르면 재생 중이던 것은 멈춘다(한 번에 하나).
음파 모양은 스타가 녹음할 때 실제 목소리 크기를 측정해서 만든다.

## 받은 사진·영상·음성 저장 — 허용, 대신 유출 금지 (2026-09-28 확정)

유료 콘텐츠라 저장을 막을지 고민했지만, **버블·위버스처럼 기기 저장은 허용**하기로 함.

- 다른 서비스: 버블은 앱 설명에 "사진/동영상 저장"이 있고 약관으로 아티스트 콘텐츠 유출(캡처
  포함)을 금지, 위버스 DM도 개인 소장 저장은 가능·공유는 금지가 일반적 이해.
- 저장을 막아도 스크린샷·화면 녹화는 막을 수 없어서(아이폰은 스크린샷 차단 불가) 실효성이 낮고,
  "돈 냈는데 저장이 안 된다"는 불만이 더 클 것으로 판단.
- 대신 **처음 저장할 때 "개인 소장용, 공유·유출 시 이용 제한" 안내에 동의**를 받는다(기기당 한 번).
  이용약관에도 유출 금지 조항을 넣는다(변호사 검토 때 같이).
- 앱 안 보관함(북마크), 배우(소속사)별 저장 켜기/끄기(계약상 요구 대비), 저장 파일에 팬 닉네임
  워터마크(유출 추적)는 **보류**(2026-09-28 결정) — 보관함은 채팅방 스크롤·폰 저장으로 충분하고 필요하면
  "사진·영상만 모아보기" 탭이 더 나음, 저장 끄기는 소속사가 계약에서 요구할 때, 워터마크는 유출 사고가 생기거나
  소속사가 요구할 때(팬이 불쾌해할 수 있고 잘라내면 사라지며 영상은 처리 비용이 큼). 화면 캡처는 어차피 못 막음.
- 배우 이름·소속사 이름은 **영어 하나로 입력**하는 운영 규칙으로 대신한다(다국어 입력 기능은 만들지 않음,
  2026-09-28 결정). 태국 배우는 원래 영어 이름으로 활동하는 경우가 많고, 팬은 이미 아는 배우를 찾아오는 거라
  배우 소개 글도 두지 않는다.

## 신고·차단·제재 정책 — 잠정안으로 개발, 출시 전 확정 (2026-09-28)

> **구현 완료(2026-09-28)** — 아래 잠정안대로. 차단은 배우 본인·소속사가 팬 답장 목록의 ⋯에서 바로 하고, "차단
> 관리"에서 해제. 신고는 운영자 목록으로만 가고, 여러 명이 신고한 메시지가 위로 온다. 팬이 스타 메시지를
> 신고하는 기능(⋯ → 신고)도 그대로 유지 — 앱스토어 신고 수단 요건 + 스타 계정 해킹·실수 대비.

> 사용자 결정(2026-09-28): 지금 다 정하려면 진도가 안 나가서, 아래 **추천안을 잠정 결정으로 두고 개발**하고
> 출시 전(변호사 검토 때) `STATUS.md` "출시 전 확정할 정책" 목록으로 한 번에 확정한다.

사용자 문제 제기: 배우·소속사·운영자 누구나 신고할 수 있는데, 몇 번 신고되면 이용을 막는지, 그때
결제는 어떻게 되는지, 소속사가 "이 팬은 우리 배우 채널에 못 들어오게 해달라"고 할 수 있어야 하는지.

**제안하는 구조 — "신고"와 "차단"과 "제재"를 나눈다**

1. **신고** — 팬(스타 메시지), 스타·소속사(팬 답장) 누구나 할 수 있다. 신고는 **운영자 검토 대기열로만**
   간다. 신고한 쪽이 직접 제재하지 않는다(소속사는 신고 처리 권한 없음 — 기존 이해상충 원칙 유지).
2. **차단(배우 채널 단위)** — 스타 본인 또는 소속사가 **운영자 없이 바로** 할 수 있다. 차단된 팬은 그
   배우에게 **답장을 보낼 수 없고, 이미 보낸 답장도 스타·소속사에게 안 보인다**. 대신 **구독·메시지
   열람은 유지**(돈 낸 기간의 권리는 건드리지 않음 → 환불 문제가 생기지 않음). 다른 배우 채널엔 영향 없음.
3. **제재(서비스 전체)** — **운영자만**. 경고 → 일시정지(기간) → 영구차단(이미 구현된 정지·차단 기능).
   **신고 횟수로 자동 제재하지 않는다** — 팬덤 간 집단 신고로 악용될 수 있어서. 대신 서로 다른 사람에게
   여러 번 신고되면 운영자 대기열 맨 위로 올리고, 그 사이 **답장만 임시 제한**하는 정도는 검토 가능.

**결제·환불**

- 결제는 애플·구글이 처리하므로 **환불 결정권도 기본적으로 스토어에 있다**. 애플은 이용자가 애플에
  직접 환불을 요청하면 애플이 판단하고, 우리가 서버에서 구독을 해지할 수도 없다. 구글은 개발자가 환불·
  구독 취소를 할 수 있다.
- **약관 위반으로 정당하게 제재된 경우 "남은 기간 환불 없음"**을 약관에 명시(업계 일반적). 다만 한국
  전자상거래법 등과 충돌하지 않는지 **변호사 검토 필요**.
- 영구차단 시엔 앱에서 "구독은 스토어에서 직접 해지해야 한다"고 안내(애플은 자동 갱신을 우리가 못 끄므로
  차단된 채로 계속 결제되는 걸 막기 위함), 구글은 서버에서 갱신을 취소.
- **소속사가 위반 없는 팬을 채널에서 내보내 달라고 하는 경우**(예: 사생 의심)는 "차단"으로 먼저 대응하고,
  구독 자체를 끊어야 한다면 **운영자 승인 + 남은 기간 환불**(팬 잘못이 아니므로) — 결정 필요.

**결정해야 할 것**
1. 배우/소속사 차단 범위: 답장만 막기(추천) vs 채널 열람까지 막기
2. 신고 누적 자동 제재: 안 함(추천) vs 일정 횟수에 자동 일시정지
3. 제재 시 환불: 약관 위반이면 우리 쪽 환불 없음(추천, 변호사 확인)
4. 소속사 요청에 의한 강제 퇴장: 운영자 승인 + 환불(추천) vs 허용 안 함

## 소속사 (2026-09-28 확정, 구현 완료)

토피에 "소속사"라는 단위를 따로 둔다. 방송사가 매니지먼트까지 겸하는 경우(예: 방송사
전속 배우)도 같은 "소속사"로 취급한다 — 소속사와 출연작 방송사를 따로 구분해야 할
일이 생기면 그때 나눈다.

- **팬에게도 보여준다.** 배우 목록/프로필에 소속사 이름이 나오고, 배우 찾기 화면에서
  소속사별로 걸러 보거나 소속사 이름으로 검색할 수 있다(예: 소속사 이름을 치면 그
  소속사 배우가 다 나옴).
- **소속사 직원은 자기 소속사 배우 전원을 본다.** 소속사 안에서 "이 매니저는 이
  배우만" 식으로 담당을 나누지 않는다. 새 배우가 소속사에 들어오면 그 소속사 직원
  모두가 바로 볼 수 있다.
- **이적하면 이전 소속사는 더 이상 못 본다** — 과거 메시지 포함. 모니터링은 "지금
  소속된 곳"만 할 수 있다.
- **대신 "언제부터 언제까지 어느 소속사였는지" 이력은 남긴다.** 이적 전후 매출을
  어느 소속사에 정산할지 나누거나, 계약 분쟁이 생겼을 때 근거로 쓰기 위한 기록이다.
- 무소속(개인 활동) 배우도 있을 수 있다.
- 소속사 등록, 배우 소속 변경(이적), 직원 계정 배정은 운영자(ADMIN)만 한다.

**아직 안 된 것**: 운영자가 이걸 누르는 화면(지금은 API만 있음). 그리고 실제 정산을
하려면 "결제 1건마다, 그 순간 어느 소속사였는지"를 적어두는 결제 기록이 따로 필요한데,
지금 구독 데이터는 매달 갱신될 때 덮어써져서 결제 건별 기록이 안 남는다 — 정산 기능을
만들 때 같이 추가하기로 함.

  "스타 콘텐츠 외부 유출 금지"를 넣는다 — 기기 저장(다운로드)은 허용하되 재배포는 금지.
- **팬 답장은 "보낸 시점의 가장 최근 스타 메시지"에 자동으로 묶인다**(2026-09-28, 버블
  방식 따름). 스타가 1·2·3번을 연달아 보낸 뒤 팬이 답장하면 3번에 대한 답장이 되고,
  팬이 과거 메시지를 골라 인용하는 기능은 두지 않는다. 팬 화면에는 인용 표시가 따로 안
  나오고(카톡처럼 대화 순서로 자연스럽게 보임), **스타 화면에서는 자기 메시지 하나마다
  달린 팬 답장을 모아서** 보여준다 → 스타가 그중 하나를 골라 인용 답장(전체 공개).
  나중에 팬도 직접 골라 인용하게 바꾸고 싶으면 같은 필드로 확장 가능.

**아직 정할 것**: 다운로드 제한(구독 해지 후 재열람, 워터마크), 파일 용량·영상 길이 제한.

## 브랜드/화면 방향

브랜드 톤, 컬러, 화면 구조(하단 탭 3개, 배우 프로필에 콘텐츠 피드 없음 등)는
[`brand-guide.md`](./brand-guide.md)에 정리.

## 콘텐츠 모더레이션 (2026-09-18 확정)

팬이 배우에게 보내는 답장에 금칙어(욕설/음란한 표현)가 있으면:

- **전송 자체를 차단**한다 — 배우에게는 아예 도달하지 않고, 팬에게 "전송되지 않았다"고
  알린다. 마스킹(`***` 치환) 방식은 쓰지 않는다.
- 금칙어 목록은 **한국어·태국어·영어** 3개 언어로 관리한다. 한국어를 포함한 이유는
  운영자(대표) 본인이 직접 목록을 관리하기 편하도록.
- "블랙리스트 관리"는 **금칙어 목록 관리**를 뜻한다(특정 팬 계정을 통째로 차단하는
  기능과는 별개 — 아래 회원 관리 참고).

### 일본어/중국어 답장 검열 방식 (2026-09-21 확정)

출시 언어를 5개로 넓히면서(위 "출시 국가·다국어 범위" 절), 금칙어 목록이 없는
일본어/중국어 답장은 지금 필터를 그냥 통과해버리는 문제가 생겼다. 일본어/중국어
단어 목록을 새로 만드는 대신 **LLM으로 답장 내용이 부적절한지 판단하는 방식**을
쓰기로 함 — 이유:
- 한국어를 금칙어 목록에 넣은 원래 이유("운영자 본인이 직접 읽고 관리하기 편해서")가
  일본어/중국어에는 적용이 안 됨(운영자가 못 읽는 언어).
- 어차피 번역 기능도 LLM 기반으로 가기로 했으니(위 절 참고), 같은 방향으로 판단
  로직도 LLM에 맡기는 게 자연스러움 — 단어 목록으로는 못 잡는 변형된 표현도 잡을
  수 있다는 부가 이점도 있음.
- **한국어/태국어/영어는 기존 단어 목록 방식 그대로 유지**한다 — 이미 만들어져
  있고 운영자가 직접 관리할 수 있어서 굳이 바꿀 이유가 없음. 즉 언어에 따라 검열
  방식이 다른 하이브리드 구조가 됨(한/태/영 = 단어 목록, 일/중 = LLM 판단).

기술적 구현은 [`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md)
참고. 구현은 아직 시작 전.

## 회원(팬) 관리 (2026-09-18 확정)

운영자가 문제 있는 팬 계정을 제재할 수 있어야 한다. 제재는 2단계:

1. **일시정지** — 정해진 기간 동안 서비스 이용 불가
2. **영구차단** — 계정을 완전히 막음

가벼운 위반은 일시정지, 심각한 위반은 영구차단으로 운영자가 상황 보고 선택한다.

**둘 다 구현 완료(2026-09-18)** — 금칙어 관리·회원 정지/차단·신고 처리를 운영자가
실제로 쓸 수 있는 화면(앱)까지 다 만들었다. 원래 신고 처리 기능조차 화면이 없어서
API로만 쓸 수 있었는데, 이번에 같이 해결함. 앱 로그인 후 운영자 계정은 이제
전용 화면(`/admin`)으로 바로 들어간다.

## 연령 정책: 만 14세 미만은 부모 동의 (2026-09-18 확정, Bubble 방식 따름)

Bubble의 실제 약관을 확인해보니 "만 14세 미만은 막지 않고 법정대리인 동의를 받는다"고
돼 있어서, 토피도 같은 방식으로 가기로 함(한국 개인정보보호법 요건과도 일치).
가입 시 생년월일을 물어보고, 14세 미만이면 부모 이메일로 확인 링크를 보내서 동의를
받는다 — 동의 전까지는 구독(결제)이 막힌다. 구현 완료.

## CP(페어링) 채팅방 (2026-09-21 확정 → 2026-09-29 구현, 아래 "커플방 구현" 절)

두 배우가 같이 나오는 "CP"(팬들이 두 배우를 하나의 커플처럼 응원하는 조합) 팬을 위한
별도 채팅방. 배우 개인방과 헷갈리지 않게 정리하면: **배우 개인방이든 CP방이든 팬
입장에서는 똑같은 "DM(채팅방)" 화면**이다 — 배우가 전체 구독자에게 보내는 메시지 +
팬 본인의 개별 답장이 한 화면에 보이는 구조. CP방은 이 구조를 그대로 쓰되, 보낸
사람이 배우 A 또는 배우 B 둘 중 하나로 표시된다는 점만 다르다.

- **결제**: CP방은 개별 배우 구독과 완전히 별개의 상품이다. 두 배우를 각각 구독
  중이어도 CP방은 자동으로 열리지 않고, 별도로 구매해야 한다(월 정액, 예: 3,000원).
  다만 "배우A 구독 + 배우B 구독 + CP방"을 한번에 묶어 사는 번들 상품을 할인가(예:
  5,000원)로 따로 만든다 — 개별로 다 사는 것보다 싸게. 번들도 결국 스토어에 등록하는
  별도 상품 하나일 뿐, 구매하면 서버가 세 가지 이용권을 한번에 부여한다.
- **발송**: 한 배우가 여러 CP방에 속할 수 있다(다른 배우와 CP를 여러 개 맺을 수
  있음). 배우가 메시지를 보낼 때 "내 개인방"이 아니라 자신이 속한 CP방 중 하나를
  골라서 보낼 수 있다.
- **답장**: 개인방과 동일하게 팬이 답장할 수 있다. 욕설·음란 표현 차단(금칙어 필터)도
  똑같이 적용된다. 답장이 배우 A/B 중 누구를 향한 건지는 구분하지 않는다 — "이 CP방에
  온 답장"으로만 취급(특정 배우 지목 답장은 이번 범위에 없음, 필요해지면 나중에 논의).
- **스토리(24시간 소멸) 기능은 CP방엔 없음** — 이번 범위에서 제외, 배우 개인방에만
  있는 기능으로 유지.
- **소속사 모니터링**: CP방을 이루는 두 배우가 서로 다른 소속사 소속일 수 있다. 각
  소속사는 자기 배우가 속한 CP방만 모니터링할 수 있어야 한다(상대 배우 쪽 소속사
  정보까지 보여줄 필요는 없음).

아직 미정: 팬 리포트(신고) 기능이 CP방 메시지에도 똑같이 붙는지, 붙는다면 화면상
어떻게 보여줄지는 구현 단계에서 기술적으로 결정(제품 관점에서는 개인방과 동일하게
신고 가능해야 한다는 것만 확정). 실제 구현은 아직 시작 전 — 기술적 스펙은
[`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md) 참고.

## 아티스트 게시글 — 구독자 전용 영구 게시판 (2026-09-21 확정)

예전 17개 질문 목록에 있던 "아티스트 게시글 작성기능"이 정확히 뭘 뜻하는지 확인한 결과:
**스토리(24시간 소멸)와 달리 계속 남아있는 게시물 목록**, 즉 구독자 전용 영구 게시판을
말하는 것이었다.

- **화면 위치 — 기존 결정에 예외 허용**: `brand-guide.md`에 "배우 프로필 화면엔
  배우정보+구독정보만, '게시물' 같은 SNS 피드성 섹션은 넣지 않는다"는 결정이 이미
  있었다. 이번 기능은 그 결정에 대한 **의도적인 예외**로, 프로필 화면에 구독자 전용
  게시판 섹션을 추가하기로 함. 단, "공개 콘텐츠 피드는 없다"는 원칙 자체는 그대로
  유지 — 비구독자에게는 여전히 안 보이고, 오직 이 기능 하나에 한해서만 프로필 화면에
  구독자 전용 섹션을 허용한다(다른 신규 기능이 생길 때 이 예외를 근거로 마음대로
  피드성 섹션을 늘리지 않을 것).
- **미디어**: 배우가 보내는 DM과 동일하게 텍스트+사진+음성+영상 지원.
- **댓글**: 팬이 텍스트+이모지로 댓글 가능(기존 DM 답장과 같은 입력 형태). **대댓글은
  1단계까지만 허용**(댓글에 답글을 달 수 있지만, 그 답글에 또 답글을 다는 건 안 됨).
- **댓글 신고**: 팬이 부적절한 댓글을 신고할 수 있고, 기존 메시지 신고와 동일하게
  ADMIN이 처리한다(소속사는 이해상충 방지 목적으로 신고 처리 권한 없음 — 기존 원칙
  그대로 연장).
- **댓글 삭제**: 배우 본인이 자기 게시물에 달린 댓글을 신고 절차 없이 직접
  삭제/숨김할 수 있다(인스타그램처럼). ADMIN의 신고 기반 처리와는 별개의 권한 —
  배우가 명백히 부적절한 댓글을 즉시 지우고 싶을 때를 위한 것.
- **소속사 모니터링**: 기존에 확정된 "배우가 실제로 뭘 보내는지 소속사가 읽기 전용
  모니터링" 원칙을 게시글에도 그대로 적용한다(신규 논의 아님, 메시지·스토리와 동일선상).

기술적 스펙은 [`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md)
참고. 구현은 아직 시작 전.

## 대화기록 보존 기간 (2026-09-21 확정)

지금까지는 메시지를 무기한 보관했는데(스토리만 24시간 후 소멸), 프라이버시
규제(개인정보 보관 기간 명시 요건) 대응과 스토리지 비용 관리를 위해 보존 기간을
정하기로 함.

- **배우가 전체 구독자에게 보내는 방송(브로드캐스트)**은 배우 본인의 콘텐츠이므로
  **계속 유지**한다 — 게시글과 마찬가지로 배우가 직접 지우기 전까지는 안 지워짐.
- **팬 개인의 답장**은 그 팬이 해당 배우 구독을 해지한 뒤 **1년이 지나면 자동
  삭제**한다. 1년 안에 다시 구독하면 삭제 대상에서 자동으로 제외된다(계속 활성
  고객이므로).
- **아티스트 게시글**도 같은 원칙: 게시물 자체는 배우가 직접 지우기 전까지 영구
  유지, 댓글은 단 팬의 댓글은 그 팬의 구독 해지 1년 뒤 삭제.
- **CP방**도 같은 원칙을 그대로 적용한다(배우가 CP방에 보낸 메시지는 유지, 팬
  답장만 구독 해지 1년 뒤 삭제) — 별도 논의 없이 기존 방과 동일 규칙 연장.
- **사진/음성/영상 같은 미디어 파일**도 텍스트와 똑같은 규칙을 적용한다(별도로 더
  짧게 지우지 않음) — 관리가 단순해지는 대신, 스토리지 비용은 파일럿 단계 규모에서는
  감당 가능하다고 판단.
- 위 기간(1년)은 확정 수치이며, 이용약관에도 명시해야 한다(현재 `terms.tsx` 초안에는
  아직 반영 안 됨 — 법률 검토 시 같이 넣을 것).

기술적 구현(정리용 cron, 삭제 조건의 정확한 기준일 등)은
[`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md) 참고.
**구현 완료(2026-09-28)** — 매일 새벽 정리. 운영자가 아직 처리하지 않은 신고가 걸린 답장은 처리될 때까지 남겨둔다.
탈퇴한 팬도 탈퇴 때 구독이 해지되므로 같은 규칙(1년 뒤 삭제). 약관 초안에도 반영.

## 출시 국가·다국어 범위 (2026-09-21 확정, 같은 날 5개 언어로 확장)

전 세계 팬을 한 번에 열기보다 좁게 시작하기로 하고, 처음엔 **태국 + 한국 +
영어권(글로벌) 3개 언어권**으로 정했다. 이유:
- 태국은 배우의 본거지 팬덤, 한국은 운영자(대표) 본인 시장, 영어는 나머지 글로벌
  팬을 폭넓게 커버.
- 언어를 더 늘릴수록 번역 품질 검증·고객지원 부담이 커짐 — 파일럿 단계엔 적을수록
  안전하다고 판단.

**같은 날 논의를 이어가며 일본어 + 해외 화교권 중국어를 추가**하기로 확정 — 최종
**5개 언어(태국어/한국어/영어/일본어/중국어)**로 시작한다. 근거:
- **일본어**: 기술적 장벽이 없고(번역 API·푸시·앱스토어 전부 글로벌 인프라 그대로
  사용 가능), 태국 BL 콘텐츠의 실제 최대 해외 소비국 중 하나라 시장 적합성이 높음.
- **중국어는 범위를 명확히 한정**: "언어 추가"와 "중국 시장 진출"은 완전히 다른
  프로젝트다. **해외 화교권(대만/홍콩/말레이시아/싱가포르 등, 글로벌 앱스토어로
  접근 가능한 팬)만 대상으로 중국어 UI를 지원**하기로 함 — **중국 본토 정식 서비스는
  이번 결정에 포함되지 않는다.** 중국 본토는 ICP 라이선스, FCM(구글 서비스) 접근
  차단으로 인한 별도 푸시 서비스 구축, 별도 결제/검열 대응까지 필요한 훨씬 큰
  프로젝트라 지금 단계의 "언어 추가"와 섞으면 안 됨 — 필요해지면 완전히 별도로
  논의할 것.
- 번역은 5개 언어 모두 지원해야 하는데, 아래에서 정리하듯 **번역 방식 자체를
  전통적 번역 API에서 LLM 기반으로 바꾸기로 하면서** 특정 언어 지원 여부보다
  번역 품질(특히 태국어의 자연스러움)이 더 중요한 기준이 됨.

**후속 확인 필요**: 금칙어(욕설/음란 표현) 필터는 현재 한국어/태국어/영어 3개
언어만 목록이 있음(운영자 본인이 관리하기 편한 언어 기준) — 일본어/중국어 UI를
열면 그 언어로 오는 팬 답장은 지금 필터를 통과해버릴 수 있음. 금칙어 목록도 같이
넓힐지는 별도 결정 필요(아직 미정, 이번 언어 확장 결정에는 포함 안 됨).

**메시지 번역은 지금 바로 실제 번역 로직에 연결하기로 함**(스캐닝만 해두고
미루지 않음) — `MessageTranslation` 캐싱 모델은 이미 있었지만 실제 번역 로직이
없었음.

**번역 엔진: "LLM 기반으로 간다"까지만 확정, 구체적 서비스(Claude/GPT/Gemini
등)는 미정 (2026-09-21)**. 처음엔 Google Cloud Translation API(전통적 기계번역)로
정했었는데, 다시 논의하면서 뒤집음 — 이유:
- 유료 서비스라 번역 품질이 나쁘면 팬이 이탈할 수 있어서 품질이 가격보다 중요한데,
  전통적 기계번역(Google Translate 등)은 태국어처럼 학습 데이터가 적은 언어에서
  품질이 눈에 띄게 떨어지고, 토피의 핵심 시나리오(배우-팬 간 다정한 대화체 DM)가
  기계번역이 제일 못하는 유형(격식 없는 대화체, 톤·감정 보존)이라는 문제 제기가 있었음.
  경쟁 서비스인 DeepL은 애초에 태국어 자체를 지원하지 않아 제외됐던 것도 같은 맥락.
  참고로 위버스는 "Quick Translation" 기능으로 태국어를 포함해 15개 언어를
  지원하고 있어(2025년 9월 업데이트), 다국어·번역 품질이 실제 업계에서도 핵심
  경쟁 요소임을 확인함.
- LLM(Claude/GPT/Gemini 등)은 문맥·톤을 이해해서 대화체 번역에 강하고, 프롬프트로
  "팬서비스 말투 유지" 같은 지침을 줄 수 있음 — 전통적 번역 API로는 불가능한 부분.
  캐싱(지연 번역) 구조 덕분에 메시지당 1회성 비용이라, 파일럿 규모(월 수천 건
  이하)에서는 어떤 LLM을 쓰든 비용 차이가 절대금액으로는 미미함(월 몇천 원 수준) —
  즉 이 규모에서는 "비용" 때문에 서비스를 고를 이유가 딱히 없고, 실제 번역 품질을
  보고 정하는 게 맞다고 판단.
- 다만 **어느 LLM(Claude/GPT/Gemini)이 실제로 더 자연스러운지는 검증 안 됨** —
  블로그성 벤치마크들이 서로 엇갈린 얘기를 해서 신뢰하기 애매함. 그래서 지금은
  "LLM 기반으로 간다"만 확정하고, 구체적으로 어느 서비스를 쓸지는 실제 팬-배우
  DM 스타일 샘플 문장으로 직접 비교해본 뒤 결정하기로 함(아직 테스트 안 함).

번역은 메시지를 받을 때마다 자동으로 모든 언어로 미리 번역해두는 방식이 아니라,
**팬이 번역 버튼을 눌렀을 때 그 언어로 한 번만 번역해서 캐시에 저장**하는 지연 번역
(lazy translation) 방식 그대로 유지 — 스키마 설계 당시 의도와 동일, 비용을 아끼기
위함(엔진을 LLM으로 바꿔도 이 구조는 그대로 재사용).

기술적 연동 방식은 [`docs/engineering/architecture-notes.md`](../engineering/architecture-notes.md)
참고. 구현은 아직 시작 전.

## 사진·음성·영상 올리기 — 서버 쪽 완료 (2026-09-28)

스타가 사진·음성·영상을 보내고 스토리를 올릴 수 있게 하는 **기반**이 생겼다(실제로 사진을
고르고 녹음하는 앱 화면은 다음 작업).

- **구독자만 볼 수 있다**: 파일은 비공개 저장소에 두고, 앱이 보여줄 때마다 서버가 "이 사람이
  볼 권한이 있는지" 확인한 뒤 잠깐(1~2시간)만 쓸 수 있는 주소를 준다. 그 주소를 다른 사람에게
  넘겨도 곧 만료된다.
- **아무 파일이나 못 올린다**: 사진·음성·영상으로 올릴 수 있는 형식과 최대 크기를 정해뒀고
  (사진 20MB, 음성 30MB, 영상 200MB — 잠정), 확장자만 바꾼 가짜 파일도 실제 내용을 확인해서
  걸러낸다.
- **스타 본인만 올릴 수 있다**(소속사·팬은 불가 — 기존 원칙 그대로).
- **24시간 스토리는 파일까지 지운다**: 시간이 지나면 기록뿐 아니라 저장된 파일도 삭제.
- 인터넷 다른 곳에 있는 사진 주소를 붙여 보내는 방식은 막았다(구독자 전용이 깨지고, 외부
  사이트가 누가 봤는지 추적할 수 있어서).

## 앱 화면 다국어 — 기반 완료 (2026-09-28)

앱 화면이 5개 언어(한국어·태국어·영어·일본어·중국어)로 나온다.

- **어떤 언어로 보이나**: 기본은 휴대폰 언어를 따라간다. 지원하지 않는 언어(예: 프랑스어)면
  영어로 보인다. 마이페이지에서 직접 바꿀 수 있고, 바꾸면 앱을 다시 켜도 유지된다.
- **중국어는 번체와 간체로 나눴다(2026-09-28 결정)** — 대상이 해외 화교권인데, 대만·홍콩은
  번체, 말레이시아·싱가포르는 간체를 쓰기 때문. 휴대폰 설정을 보고 자동으로 고른다. 그래서
  화면 언어 선택지는 6개(한국어, ไทย, English, 日本語, 简体中文, 繁體中文).
- **알림도 그 언어로** 간다. 카톡처럼 알림 제목은 배우 이름, 내용은 메시지 미리보기이고,
  사진·음성·영상만 보낸 경우엔 "사진을 보냈어요" 같은 안내가 팬의 언어로 나온다.
- **한국어로만 남겨둔 것**: 운영자 화면(운영자 본인용), 이용약관·개인정보처리방침 본문(변호사
  검토 후 최종본이 나오면 그때 언어별로 번역 — 지금은 "초안이며 한국어로만 제공" 안내만 각
  언어로 나옴).
- **아직 안 된 것**: 배우 이름·소개, 소속사 이름처럼 운영자가 입력하는 내용은 입력한 언어
  그대로 보인다(언어별로 따로 입력받는 기능은 후속). 서버가 보내는 일부 오류 문구도 아직
  한국어.
- **번역 품질**: 태국어·일본어·중국어 문구는 기계로 작성한 것이라 **출시 전 원어민 검수 필요**.

## 소속사 계약/정산 조건 — 논의만 함, 미확정 (2026-09-21)

**확정 아님** — 업계 보편적인 구조를 참고용으로 얘기해본 것뿐, 실제 조건은 사용자가
직접 협상해서 정할 사업 영역이다. 논의 내용만 참고삼아 남겨둔다:

- 비율은 토피(플랫폼) : 소속사 사이의 순수익(앱스토어 수수료 제외 후) 배분을 말함.
- "6:4"는 소속사 60% / 토피 40% + 플랫폼이 소속사에게 선급금(계약금)을 지급하고
  향후 정산금에서 차감 회수하는 구조.
- "7:3"은 계약금 없이 소속사 70% / 토피 30% — 초기 현금 부담 없이 시작하되 장기
  배분율을 더 후하게 주는 구조.
- 일반적으로 플랫폼이 검증되지 않은 초기 단계·첫 파트너 확보 단계에서는 계약금 없이
  배분율을 높게 주는 방식(7:3)이 흔하고, 플랫폼이 자금 여력이 있거나 이미 검증된
  경우엔 선급금으로 좋은 파트너를 락인하는 방식(계약금+6:4)을 쓰는 경향이 있다는
  점을 참고로 얘기함. 트랙레코드가 쌓이면 다음 파트너부터 배분율을 조정해나가는 게
  자연스럽다는 의견도 논의했다.
- 계약 기간·독점 조항·해지 조건 등 나머지 세부 조항은 아직 논의 안 함.

## 스타 화면 "팬 답장 줄"과 답장 채팅 화면 — 1차에 추가 (2026-09-28)

버블·위버스처럼, 스타가 메시지를 보내면 그 아래에 **팬 답장 줄**이 생기고, 누르면 **답장 채팅 화면**이 열린다.
답장이 쏟아지는 걸 보는 게 스타 입장에서 이 서비스의 핵심 재미라 1차에 넣음(사용자 결정).

- **답장 줄**: 최근 메시지 10개 아래. 팬 답장이 **온 순서대로** 한 줄씩(2.5초마다) 위로 넘어가며 보이고, 새 답장이
  와도 건너뛰지 않고 차례가 되면 이어서 보여준다(최근 20개를 돌아가며). 답장이 아직 없으면 "팬 답장을 기다리는
  중…". 그보다 오래된 메시지는 "팬 답장 N개" 숫자만.
- **답장 채팅 화면**: 위에 스타 메시지 고정, 팬 답장은 말풍선으로 **오래된 게 위·새 답장이 맨 아래**(카톡·라이브
  채팅과 같은 방향, 팬 채팅방과도 통일 — 2026-09-28 사용자 결정). 화면은 맨 아래(최신)에서 시작하고, 맨 아래를
  보고 있으면 새 답장을 따라 화면이 올라간다. 위로 올려 예전 답장을 읽는 중이면 끌어내리지 않고 "새 답장 N개 ↓"
  버튼만 띄운다. 위 끝까지 올리면 이전 답장을 100개씩 더 불러온다(답장이 수천 개여도 느려지지 않게).
- 답장마다 닉네임 + 구분 태그. 신고·차단·답장하기(인용)는 말풍선 옆 ⋯ 메뉴로(채팅 느낌을 살리려고 버튼을 늘어놓지 않음).
- 답장 줄은 눈에 잘 띄는 자리라 더 엄격하게 거른다 — 이 채널에서 차단된 팬, 정지·탈퇴한 팬, 신고 처리된 답장은
  빼고 닉네임만(태그는 채팅 화면에서만).
- 지금은 "자주 새로고침"(채팅 화면 3초, 메시지 목록 5초)으로 거의 실시간처럼 보이게 했고, 진짜 실시간 연결은
  호스팅이 정해진 뒤 바꾼다(화면은 그대로 씀). 휴대폰에서 "동작 줄이기"를 켠 사람에겐 넘어가는 효과 없이 바뀐다.

## 실시간 채팅 (2026-09-29)

## 묶음(패키지) 구독 — 만듦 (2026-09-29)

여러 배우 개인방을 개별로 구독할 때보다 싼 값에 한 번에 파는 상품(사용자 결정: 지금 만들 수 있으면 진행).

- **팬이 보는 것**: 배우 프로필 아래 "묶음으로 더 저렴하게" — 묶음 이름, 월 가격, "따로 구독보다 N% 할인". 누르면 묶음 구독
  화면(포함된 배우와 각자 따로 구독할 때 가격, 혜택). 사면 포함된 배우 채팅방이 모두 열린다.
- **이미 개인 구독 중인 배우가 묶음에 있으면**: 그 개인 구독은 묶음으로 옮겨지고 대화는 끊기지 않고 이어진다(구매 전에
  안내). 실제 결제가 붙으면 스토어 구독은 앱이 대신 해지할 수 없어서, 그때는 "스토어에서 개인 구독을 해지해 주세요" 안내로 바뀐다.
- **해지**: 묶음 단위로. 묶음으로만 열린 배우 채팅방에서 해지를 누르면 "묶음에 든 다른 배우 방도 함께 닫혀요"라고 먼저 알려준다.
  따로 개인 구독한 배우는 묶음을 해지해도 그대로.
- **운영자**: "묶음 상품" 화면에서 이름·가격·배우(2명 이상)·스토어 상품 ID 등록, 판매 중지(이미 산 팬은 유지). 구독 중인 팬이
  있는 묶음은 배우 구성을 바꿀 수 없다(이미 산 사람의 방이 갑자기 바뀌면 안 돼서 — 새 묶음으로). 가격·상품 변경은 작업 기록에 남음.
- **정산 배분(잠정)**: 묶음 가격을 포함된 배우들의 개인 구독 정가 비율대로 나눠 기록 — 예) 개인 ฿129 + ฿99를 묶음 ฿179로 팔면
  ฿101 / ฿78. 소속사 계약서에 이 방식을 적어야 함.
- **예전 방식 정리**: "짝꿍 배우를 이미 구독 중이면 N% 할인" 안내는 없앰 — 스토어 결제는 상품마다 가격이 고정이라 "이 사람만
  할인"이 불가능해서, 묶음 상품이 그 역할을 대신함.
- **커플(CP)방**: 커플방 기능(2차)을 만들 때 묶음에 커플방도 넣을 수 있게 구조를 잡아 둠(예: 배우 A + 배우 B + 커플방).

## 사진·영상 보기를 카톡 수준으로, 모아보기·복사·음성 이어 듣기·끊김 표시 (2026-09-29)

사용자: "카톡처럼 기본으로 있어야 하는 것들" → 1차에 모두.

- **전체 화면**: 두 손가락으로 벌리거나 두 번 탭하면 확대, 확대한 채로 끌어서 이동. 좌우로 넘기면 그 채팅방의 이전·다음
  사진·영상(왼쪽이 이전). 위아래로 끌면 닫힘. 위에 보낸 날짜와 "3 / 12". 저장 버튼은 지금 보는 것. 컴퓨터 브라우저에선 좌우 화살표.
- **사진·영상 모아보기**: 채팅방 오른쪽 위 버튼 → 받은 사진·영상을 최신순 격자로. 예전엔 "채팅방 스크롤로 충분"이라 보류했지만,
  대화를 50개씩 나눠 불러오는 구조라 오래된 사진을 찾기 어려워서 1차로 당김.
- **흐린 미리보기**: 사진이 도착하는 동안 빈 칸 대신 그 사진의 흐린 모양을 먼저 보여줌(스타가 폰 앱에서 보낼 때 계산해 둠).
- **복사**: 말풍선을 길게 누르면 복사(스타 메시지·내 답장). 스타 메시지는 신고도 같은 메뉴.
- **음성 이어 듣기**: 음성 메시지 하나가 끝나면 다음 음성이 이어서 재생. 무음 모드여도 들리고 화면을 끄거나 다른 앱으로 가도 계속.
- **인터넷 끊김 표시**: 연결이 끊기면 화면 위에 작게 알려줌 — "앱이 멈췄나?" 대신 이유를 알게.
- 공유 버튼은 넣지 않음(스타 콘텐츠 외부 유출 금지 원칙). 채팅방 안 검색은 2차 후보.

## 커플방 구현 (2026-09-29)

사용자 결정: 2차였던 커플방을 앞당겨 만듦, 방식은 "방 개념 통합"(개인방과 같은 코드) + 추천 기본값.

- **만드는 사람**: 운영자가 두 배우를 골라 커플방을 만듦 — 공식 이름·**공식 사진(프로필처럼 쓰는 사진)**·월 가격.
  **방 메인(대화방) 사진과 방 이름은 두 배우가 각자 바꿀 수 있음**(1인 방에서 배우가 바꾸는 것과 같게 — 사용자 결정). 같은 두
  배우의 커플방은 하나만.
- **보내기**: 두 배우 누구나. 팬 화면 말풍선 위에 보낸 배우 이름·사진, 알림은 "방 이름" 제목에 "보낸 배우: 내용". 스타 화면에서도
  누가 보냈는지 보임. 스토리는 커플방에 없음.
- **팬**: 배우 프로필 아래 "커플방", 둘러보기의 "커플방" 줄에서 찾고, 개인 구독과 따로 구독(묶음에도 넣을 수 있음 — 예: A + B + 커플방).
  답장·신고·사진 모아보기 등은 개인방과 같음.
- **스타**: 스튜디오 첫 화면에서 "개인방 / 커플방"을 골라 들어감.
- **소속사**: 자기 배우가 든 커플방만 보고, 새 메시지 알림도 두 배우의 소속사 모두에게.
- **차단·신고**: 방 단위. 두 배우와 각 소속사 누구나 이 방에서 팬을 차단할 수 있음.
- **활동 종료**: 멤버 한 명이라도 활동을 종료하면 새 구독 중지(기존 팬은 계속).
- **정산(잠정)**: 커플방 매출은 두 배우(소속사)가 반씩 — 정산 기능 만들 때 반영.
- 예전 "짝꿍 할인"용 내부 데이터(GlCp)는 없앰(묶음 상품이 대신함).

## 채팅방 안 검색 (2026-09-29)

사용자 결정: 보류였던 채팅방 안 검색을 1차에.

- **어디서**: 채팅방 오른쪽 위 🔍 → 화면 위에 검색창이 열림(카카오톡 방 안 검색과 같은 방식 — 결과 목록 화면으로 따로 가지 않음).
- **어떻게**: 두 글자 이상 입력하면 그 방에서 찾은 개수("2/7")가 보이고, ▲(더 예전)·▼(더 최근)로 결과를 옮겨 다니면 대화가 그
  메시지로 이동해 테두리로 강조됨. 오래된 대화라 아직 안 불러온 부분이면 알아서 더 불러와서 찾아감(최대 1,000개 전까지 — 그보다
  더 예전이면 "이 메시지까지 불러오지 못했어요").
- **무엇을 찾나**: 팬이 볼 수 있는 대화만 — 구독 시작 이후의 스타 메시지와 내 답장(다른 팬 답장은 원래 안 보이므로 검색도 안 됨). 스타가
  지운 메시지는 안 나옴. 스타 메시지 속 "{팬 이름}" 자리는 내 이름으로 바뀐 채로 검색됨(예: 내 닉네임으로 찾으면 나를 불러 준 메시지).
- **검색 중엔** 답장 입력창을 잠깐 숨김(검색 닫으면 다시 나옴).

## 정산과 PC용 넓은 화면 (2026-09-29)

사용자 결정: 정산(결제 기록 기준, 커플방·묶음 배분 포함)과 PC용 넓은 화면을 지금.

**무엇을 기준으로 계산하나** — "결제 기록". 팬이 결제할 때마다(첫 결제, 매달 갱신) 한 건씩 적고, 그 순간에 이 돈이 **어느 배우 몫이고
그 배우가 어느 소속사였는지**를 같이 고정해 둔다. 그래서 나중에 배우가 소속사를 옮기거나 가격이 바뀌어도 지난 정산은 그대로다(이적
전에 들어온 돈은 이전 소속사 몫). 팬이 탈퇴해도 결제 기록은 남는다(세무·정산 근거).

**나누는 규칙(잠정)**:
- 개인방: 그 배우 100%.
- 커플방: 두 배우가 반씩.
- 묶음: 들어 있는 방들의 개인 정가 비율로 나눈 뒤, 커플방 몫은 다시 반씩. 예) 배우 A ฿3,000 + 배우 B ฿3,000 + A·B 커플방 ฿6,000을
  묶음 ฿8,000에 팔면 A 방 2,000 / B 방 2,000 / 커플방 4,000 → A 4,000, B 4,000.

**한 달 정산 표**: 결제액 → 스토어 수수료(잠정 15%) → 남은 금액을 소속사 몫(잠정 70%) / 토피 몫(30%)으로. 무소속 배우는 배우 본인에게
같은 비율. 소속사마다 계약이 다를 수 있어서 운영자 "소속사 관리"에서 소속사별 비율을 따로 정할 수 있고, 바꾸면 작업 기록에 남는다.
환불된 결제는 빼고 "환불" 칸에 따로 보인다. 한 달은 태국 시간 기준.

**누가 어디서 보나**: 운영자는 전체(소속사 골라 보기), 소속사는 자기 소속사 배우만. **PC 웹에서만** 보이고(표가 크고 민감한 정보라 —
2026-09-28 결정), 배우별·방별 CSV로 내려받아 엑셀에서 열 수 있다. 개발·데모 환경에선 결제 없는 테스트 구독도 "테스트 결제 포함"으로 볼
수 있다(운영에선 없음).

**주의**: 지금 숫자는 앱에 적힌 가격(바트) 기준 추정이다. 실제로 들어오는 돈은 나라별 스토어 가격·환율·세금 때문에 조금 다르므로, 스토어
결제를 연결한 뒤엔 애플·구글 정산 보고서와 맞춰 보고 지급한다. (→ 아래 "정산 마감"·"정산 지급 기록"으로 해결됨) "이 달 정산 확정(마감)" 기능은 아직 없다 — 지난달에 환불이 들어오면
그 달 숫자가 바뀔 수 있어서 지급할 때 CSV를 받아 보관해 둔다.

**PC용 넓은 화면**: 운영자·소속사 화면을 PC 브라우저(가로 1024 이상)로 열면 왼쪽에 메뉴가 고정되고 오른쪽에 내용이 넓게 보인다. 폰과
좁은 창은 지금처럼. 같은 코드라 앱을 따로 만들지 않음.

## 결제·소셜 로그인 — 코드 미리 작성 (2026-09-29)

사용자 결정: 계정·키 등록은 나중에 하되, 코드로 할 수 있는 건 미리 다 짜 둠. **키를 넣으면 켜지고, 없으면 지금처럼**(테스트 구독·개발용
로그인) 동작한다. 넣어야 하는 값 목록은 `ops-infra-backlog.md` "결제·로그인 키 넣기".

**로그인 화면**
- 앱: 애플·구글·LINE·카카오·네이버 버튼 — 키가 들어간 것만 보임. 한국어로 쓰는 사람에겐 카카오·네이버가 위, 그 외(태국·일본·대만)엔
  LINE이 위. 애플 로그인은 iOS에서 항상(다른 소셜 로그인이 있으면 애플 심사 규칙상 필수).
- PC 웹(소속사·운영자가 주로 씀): 구글 로그인 버튼. 카카오·네이버·LINE·애플 웹 로그인은 필요해지면 추가(서버 작업이 조금 더 필요).
- 운영 빌드엔 개발용 이메일 로그인이 안 보임(서버에서도 막힘).
- 보안 보강: 카카오 로그인 토큰이 **토피 앱에서 발급된 것인지** 확인(예전엔 다른 카카오 앱 토큰으로도 통과할 수 있었음). 운영·개발 앱처럼
  앱이 둘이어도 로그인되게.

**결제(구독)**
- 배우·커플방·묶음에 스토어 상품 ID가 등록돼 있으면 앱에서 **애플·구글 결제창**이 뜨고, 결제가 끝나면 서버가 스토어에 진짜인지
  확인한 뒤 방을 연다. 상품 ID가 없거나 웹이면 지금처럼 테스트 구독.
- 서버가 막는 것: 다른 배우 상품의 영수증으로 이 방 열기, 만료된 영수증, **다른 계정의 영수증**(결제창에 우리 회원 번호를 심어 둬서
  영수증 공유가 안 됨).
- 매달 갱신·결제 실패·만료·환불은 **스토어가 서버에 직접 알려 줌**(앱을 안 켜도 반영). 갱신되면 정산용 결제 기록이 쌓이고, 만료되면 방이
  닫히고, 환불되면 그 결제는 정산에서 빠지고 방도 닫힌다. 결제 실패 후 스토어가 재시도하는 유예 기간엔 계속 이용.
- 알림이 누락돼도 만료일이 하루 지난 구독은 서버가 스스로 닫음(매시간 확인). 잘못 닫혀도 "구매 복원"으로 다시 열림.
- **해지**: 스토어에서 결제한 구독은 앱이 끊을 수 없어서(애플·구글 정책) "해지" 버튼이 스토어 구독 관리 화면으로 안내한다 — 결제 기간
  끝까지는 계속 이용. (예전 방식대로 앱에서 방만 닫으면 결제는 계속되는데 방만 닫히는 문제가 있었음 — 서버도 막아 둠.)
- **구매 복원**(스토어 심사 필수): 구독 관리 아래 버튼 — 폰을 바꿨을 때 스토어 구독을 이 계정에 다시 연결.
- 묶음을 살 때 이미 개인 스토어 구독 중인 배우가 있으면 "묶음을 산 뒤 스토어에서 개인 구독을 해지해 주세요"라고 먼저 알림.

**남은 것**: 스토어·로그인 콘솔 등록과 키 입력(👤), 실제 폰으로 로그인·결제(샌드박스 계정) 확인 — 로그인·결제 SDK는 폰에서만 동작해서
웹 화면으로는 확인할 수 없다.

## 정산 마감 (2026-09-29)

- **왜**: 지난달 결제가 나중에 환불되면 지난달 정산 숫자가 바뀌어서, 이미 지급한 금액과 화면이 달라지는 문제가 있었음.
- **어떻게**: 달이 끝나면 운영자가 정산 화면에서 **"이 달 마감"**을 누른다. 그 순간의 정산표가 그대로 저장되고, 이후엔 누가 봐도(소속사 포함)
  같은 숫자가 보인다(자물쇠 표시 + 언제·누가 마감했는지). 지급은 마감한 표(CSV) 기준으로.
- **마감 뒤에 생긴 일**: 환불은 환불된 달의 정산에서 **"조정(지난달)"** 칸에 마이너스로, 늦게 기록된 지난달 결제는 플러스로 들어간다.
  조정 때문에 그 달 지급액이 음수가 되면 다음 지급에서 뺀다.
- **순서**: 앞 달부터 마감(앞 달이 열려 있으면 거절). 실수했으면 "마감 취소"로 되돌릴 수 있지만 뒤 달부터 — 이미 지급했다면 취소하지 말고
  다음 달 조정으로 처리하는 게 안전하다. 마감·취소는 작업 기록에 남는다.
- 마감은 운영자만, 소속사는 마감 상태와 숫자를 보기만.

## 정산 지급 기록 (2026-09-29)

- **왜**: 마감한 표로 돈을 보낸 뒤 "언제, 얼마를, 어떤 이체로 보냈는지"가 엑셀·메신저에만 남으면 나중에 소속사 문의나 분쟁 때 찾기 어렵다.
- **어떻게**: 실제 송금은 지금처럼 은행에서 하고, 정산 화면(마감한 달)의 각 소속사 표 아래 **"지급 기록"**을 눌러 보낸 금액·보낸 날·이체 번호·메모를
  적는다. 금액은 표의 지급액이 미리 채워지고, 은행 수수료 등으로 다르게 보냈으면 고쳐 적으면 된다(표와 다르면 화면에 같이 표시).
- **받는 쪽**: 소속사는 소속사 한 번에, 무소속 배우는 배우마다 따로. 한 달에 받는 쪽 하나당 한 번. 보낼 금액이 0원 이하(환불 조정으로 음수)면
  기록할 게 없고 "다음 지급에서 차감" 안내만.
- **소속사도 확인**: 소속사 콘솔 정산 화면에서 자기 소속사의 "지급 완료 — 날짜, 금액, 이체 번호"가 보인다. CSV에도 지급일 열.
- **실수 바로잡기**: 잘못 적은 기록은 운영자가 지우고 다시 적을 수 있다(기록만 지워지고 송금은 그대로, 작업 기록엔 남음).
- **지급 기록이 있는 달은 마감 취소 불가** — 이미 돈이 나간 표를 다시 계산하면 숫자가 어긋나기 때문. 차이는 다음 달 조정으로 처리.

## PC 웹 소셜 로그인 — 카카오·네이버·LINE 추가 (2026-09-29)

- PC 웹 로그인 화면에 구글 외에 **카카오·네이버·LINE** 버튼(키를 넣은 것만). 누르면 그 회사 로그인 페이지로 갔다가 토피 웹으로 돌아와 로그인된다.
- **앱과 같은 계정**: 회사 콘솔에서 앱용으로 만든 것(카카오 앱·네이버 애플리케이션·LINE 채널)에 "웹"을 추가해서 쓴다 — 따로 새로 만들면 같은
  사람이 다른 회원으로 잡힘.
- 안전장치: 로그인하러 떠날 때 무작위 표식을 저장해 두고 돌아올 때 같은지 확인(남이 만든 로그인 링크로 로그인되는 것 방지), 서버는 등록한 토피
  웹 주소로 돌아온 요청만 받음.
- 애플 웹 로그인은 따로 준비할 게 많아서(전용 ID·서명 키) 필요해지면 추가 — 소속사·운영자는 다른 로그인으로 충분.
  → **2026-09-29 추가함**: 같은 방식으로 "Apple로 계속하기"(키를 넣으면 보임). 앱에서 애플로 가입한 사람이 PC에서도 같은 계정으로 로그인된다.
  애플은 웹에서 이름·이메일을 받으려면 다른 방식(서버로 바로 보내기)이 필요해서, 웹에선 이름·이메일 없이 로그인만 — 웹은 주로 이미 가입한
  소속사·운영자가 쓰니 문제없음. 애플은 https 주소만 허용해서 배포한 웹 주소에서만 동작한다.

## 스타 장기 미발송 알림 (2026-09-29)

사용자 제안: 소속사·운영자만이 아니라 **배우 본인에게도 푸시**. 배우가 스스로 챙기게 하는 게 가장 효과적이라 먼저 배우에게.

- **3일째** 안 보내면(구독 팬이 있는 방만): 배우에게 "팬 42명이 기다리고 있어요 · 마지막 메시지가 3일 전이에요. 짧은 인사라도 남겨 볼까요?"
- **7일째**: 배우에게 한 번 더 + **소속사 직원에게** "OO님이 7일째 메시지를 보내지 않았어요".
- 그 뒤로는 **7일마다 한 번**(매일 울리지 않게). 메시지를 보내면 처음부터 다시 센다.
- 보내는 시각: 태국 시간 낮 12시(밤에 안 울리게). 커플방은 두 배우 모두에게 방 이름과 함께.
- 알림을 누르면 배우는 그 방 스튜디오, 소속사는 모니터링 화면으로.
- 운영자·소속사 배우 목록에 "마지막 메시지 N일 전"이 보이고 7일 이상이면 빨간색.
- 기준(3일/7일)은 잠정 — 설정값으로 바꿀 수 있음. 소속사 계약의 "최소 발송 빈도"를 정하면 거기에 맞추면 됨.

## 메시지 번역 — 만듦 (2026-09-29)

사용자 결정: 글로벌 서비스라 번역은 필수. 예전 결정(LLM으로, 누를 때만 한 번 번역해 저장)대로 만듦.

- **어디에**: 팬 채팅방의 스타 메시지, 스타 답장 화면의 팬 답장. 글이 지금 앱 언어와 **다른 글자**(한글·태국 문자·일본어·한자·영문)로 쓰였으면
  말풍선 아래에 작게 "번역 보기". 누르면 원문 아래에 번역이 붙고(원문은 그대로 — 번역이 틀릴 수 있어서), 다시 누르면 접힘.
- **비용**: 메시지 × 언어마다 한 번만 번역해 저장 — 같은 스타 메시지를 태국 팬 1,000명이 눌러도 태국어 번역은 1번. 누르지 않은 메시지는 번역 안 함.
- **말투**: "배우가 팬에게 보내는 다정한 반말 그대로, 이모지·줄바꿈 유지, 설명 붙이지 말 것"으로 지시. 스타 메시지의 "{팬 이름}" 자리는 그대로
  두고 번역한 뒤 각 팬 이름으로 채움.
- **엔진**: Claude(Anthropic). 모델은 설정 하나로 바꿀 수 있음(기본은 가장 좋은 품질의 모델 — 비용을 줄이려면 가벼운 모델로 바꿔 품질 비교).
  키를 받으면 `scripts/translation-sample.mjs`로 배우·팬 말투 예문을 6개 언어로 돌려 보고 정하면 됨. GPT·Gemini와도 비교하고 싶으면 같은 모양으로 엔진을
  하나 더 붙일 수 있게 만들어 둠.
- 키가 없을 때: 개발 서버는 가짜 번역("[th] 원문")으로 화면 확인, 운영 서버는 "번역 준비 중".
- 남은 것: 일본어·중국어 팬 답장 검열(LLM)은 같은 엔진으로 다음에.
